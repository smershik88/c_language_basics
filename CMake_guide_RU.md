# Руководство по корневому CMakeLists.txt

## 1. Назначение конфигурации

Корневой `CMakeLists.txt` задаёт единые правила сборки учебных проектов на C:

- выбирает стандарт C11 и отключает GNU-расширения;
- подключает общие предупреждения GCC и Clang;
- добавляет отдельные предупреждения, специфичные для GCC или Clang;
- по CMake-опциям включает дополнительные анализаторы и более строгие правила;
- при необходимости инструментирует код санитайзерами;
- предоставляет функцию `enable_common_checks()`, которую вызывают CMake-файлы отдельных заданий.

Флаги передаются не всему проекту глобально, а через интерфейсные цели `common_warnings` и `common_sanitizers`. Это позволяет подключать настройки явно к каждой цели.

## 2. Стандарт языка C

В корневом файле установлено:

```cmake
set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)
set(CMAKE_C_EXTENSIONS OFF)
```

Значение параметров:

- `CMAKE_C_STANDARD 11` — компилировать исходники на стандарте C11;
- `CMAKE_C_STANDARD_REQUIRED ON` — не разрешать CMake молча выбрать более старый стандарт;
- `CMAKE_C_EXTENSIONS OFF` — использовать стандартный режим (`-std=c11`), а не режим с расширениями компилятора (`-std=gnu11`).

Чтобы перейти на C99, поменяй `11` на `99`. Для этого лучше использовать отдельный каталог сборки либо очистить старую конфигурацию, если менялся компилятор.

## 3. Как подключать проверки к учебным заданиям

В каждом подкаталоге сначала создаётся цель, затем к ней вызывается `enable_common_checks()`.

Пример `hw_1/CMakeLists.txt`:

```cmake
add_executable(hw_1
    main.c
    helpers.c
)

enable_common_checks(hw_1)
```

Для нескольких исполняемых файлов функцию вызывают для каждого:

```cmake
add_executable(hw_1 main.c)
enable_common_checks(hw_1)

add_executable(hw_1_tests tests.c)
enable_common_checks(hw_1_tests)
```

Если в задании есть собственная библиотека, к ней также можно подключить проверки:

```cmake
add_library(hw_1_lib STATIC helpers.c)
enable_common_checks(hw_1_lib)

add_executable(hw_1 main.c)
target_link_libraries(hw_1 PRIVATE hw_1_lib)
enable_common_checks(hw_1)
```

Важный момент для санитайзеров: исходный код библиотеки должен быть инструментирован при компиляции, а runtime санитайзера должен быть подключён при линковке конечного исполняемого файла. Поэтому вызывай функцию и для собственной библиотеки, и для исполняемого файла, который её использует.

Если `enable_common_checks()` не вызвать для цели, интерфейсные параметры к этой цели не применятся. Само создание `common_warnings` не включает предупреждения автоматически.

## 4. CMake-опции, управляющие дополнительными проверками

Это **CMake cache options**, создаваемые командой `option()`. Это не макросы препроцессора C и не `#define`. Их задают при конфигурации через `-DИМЯ=ON` или `-DИМЯ=OFF`.

| Опция | Значение по умолчанию | Действие |
|---|---:|---|
| `ENABLE_GCC_ANALYZER` | `ON` | Для GCC добавляет `-fanalyzer`. Для других компиляторов пропускается с информационным сообщением. Проверка поддержки выполняется при конфигурации. |
| `ENABLE_CLANG_UNSAFE_BUFFER` | `OFF` | Для Clang добавляет `-Wunsafe-buffer-usage`, если компилятор поддерживает этот флаг. Может выдавать много диагностик даже в намеренно низкоуровневом корректном коде. |
| `ENABLE_AGGRESSIVE_GCC_WARNINGS` | `OFF` | Для GCC добавляет `-Wstringop-overflow=4` — строгий анализ переполнений при строковых и memory-операциях — и `-Warray-bounds=2`, который дополнительно проверяет промежуточные результаты арифметики указателей. Возможны дополнительные предупреждения и ложные срабатывания. |
| `ENABLE_STRICT_ERRORS` | `OFF` | Превращает выбранные диагностики в ошибки: неявное объявление функций, implicit int, несовместимые указатели и преобразования, ошибки типа возврата, отсутствие строгих прототипов. Это **не** глобальный `-Werror`. |
| `DISABLE_VLA` | `OFF` | Добавляет `-Werror=vla`: использование массивов переменной длины становится ошибкой. Сам стандарт C11 допускает реализацию VLA как необязательную возможность. |
| `ENABLE_C_COMPAT_WARNINGS` | `OFF` | Добавляет `-Wdeclaration-after-statement` для GCC/Clang, а для GCC также `-Wc90-c99-compat` и `-Wc99-c11-compat`. Стандарт проекта при этом остаётся C11. |
| `ENABLE_SANITIZERS` | `OFF` | Для GCC включает AddressSanitizer и UndefinedBehaviorSanitizer; для Clang — AddressSanitizer, UndefinedBehaviorSanitizer и Integer Sanitizer. Проверяется возможность компиляции и линковки набора. |

### 4.1. Статический анализатор GCC

`ENABLE_GCC_ANALYZER=ON` включён по умолчанию. GCC `-fanalyzer` анализирует возможные пути исполнения и способен находить некоторые ошибки управления ресурсами, времени жизни памяти, разыменования указателей и работы с файлами.

Это статический анализ: исполнять программу для самого анализа не требуется. Однако анализатор не доказывает отсутствие ошибок и может увеличить время компиляции. Для Clang эта опция пропускается.

Отключение:

```bash
-DENABLE_GCC_ANALYZER=OFF
```

### 4.2. Небезопасная работа с буферами в Clang

`ENABLE_CLANG_UNSAFE_BUFFER=ON` добавляет `-Wunsafe-buffer-usage`. Флаг помогает находить участки кода с указателями, индексированием и доступом к буферам, которые требуют внимательной проверки границ.

Это диагностический профиль, а не автоматическое доказательство выхода за границы. Он может подсвечивать обычные операции с указателями, особенно в учебных примерах. В текущей конфигурации поддержка флага предварительно проверяется; неизвестный флаг Clang повышается до ошибки только во время пробной проверки.

Включение:

```bash
-DENABLE_CLANG_UNSAFE_BUFFER=ON
```

При использовании GCC опция не добавляет Clang-флаг и выводит информационное сообщение.

### 4.3. Строгий режим ошибок

`ENABLE_STRICT_ERRORS=ON` превращает в ошибки только выбранные важные диагностики. Это удобно, когда базовые предупреждения уже разобраны и нужно запретить возвращение определённых классов ошибок.

В отличие от глобального `-Werror`, этот режим не превращает каждое предупреждение в ошибку. Поэтому менее критичные диагностические сообщения, например о стиле, по-прежнему остаются предупреждениями.

Включение:

```bash
-DENABLE_STRICT_ERRORS=ON
```

### 4.4. Запрет VLA

`DISABLE_VLA=ON` превращает предупреждение `-Wvla` в ошибку компиляции. Это проектное ограничение, а не требование C11: VLA — необязательная возможность C11 и стандартная возможность C99.

Включение:

```bash
-DDISABLE_VLA=ON
```

### 4.5. Совместимость со старыми редакциями стандарта

`ENABLE_C_COMPAT_WARNINGS=ON` включает предупреждения, помогающие придерживаться стиля C90 и видеть использование возможностей, добавленных в C99/C11.

При этом `CMAKE_C_STANDARD` остаётся равным 11. Если требуется именно собрать проект в режиме C90 или C99, нужно изменить `CMAKE_C_STANDARD` и конфигурировать сборку отдельно.

Включение:

```bash
-DENABLE_C_COMPAT_WARNINGS=ON
```

### 4.6. Агрессивные проверки строковых операций GCC

`ENABLE_AGGRESSIVE_GCC_WARNINGS=ON` добавляет `-Wstringop-overflow=4` и `-Warray-bounds=2`. Первый флаг усиливает диагностику потенциальных переполнений при операциях со строками и памятью. Второй расширяет проверку массивов и промежуточных результатов арифметики указателей. Эти режимы могут выдавать больше предупреждений и ложных срабатываний, особенно в сложных случаях, где компилятор не располагает всей информацией о размерах объектов.

Включение:

```bash
-DENABLE_AGGRESSIVE_GCC_WARNINGS=ON
```

### 4.7. Санитайзеры

`ENABLE_SANITIZERS=ON` инструментирует исходный код и подключает соответствующие runtime-библиотеки при линковке.

- **AddressSanitizer (ASan)** обнаруживает многие ошибки доступа к памяти: выходы за границы, use-after-free, double-free и некоторые другие ошибки.
- **UndefinedBehaviorSanitizer (UBSan)** обнаруживает выбранные виды неопределённого поведения, например некоторые недопустимые сдвиги, выравнивание, разыменование нулевых указателей и знаковое переполнение.
- **Integer Sanitizer в Clang** дополнительно обнаруживает некоторые подозрительные целочисленные операции, включая беззнаковое переполнение и потери данных при неявных преобразованиях. Беззнаковое переполнение само по себе определено стандартом C, но часто является логической ошибкой.

Санитайзеры обнаруживают ошибки только в тех путях кода, которые реально выполняются. После сборки необходимо запускать программу и тестовые сценарии. Санитайзеры предназначены прежде всего для разработки и тестирования, а не для обычной release-сборки.

Для диагностической сборки рекомендуется `Debug` и отладочная информация. У Clang документация ASan также рекомендует `-O1` или выше для разумной производительности и `-fno-omit-frame-pointer` для более информативных стеков вызовов.

Включение:

```bash
-DENABLE_SANITIZERS=ON
```

При включении CMake проверяет, что компилятор может скомпилировать и слинковать тестовую программу с нужным набором санитайзеров. Если runtime или поддержка отсутствуют, конфигурация завершается с ошибкой.

## 5. Примеры конфигурации и сборки

### 5.1. Обычная сборка GCC

```bash
cmake -S . -B build-gcc \
  -DCMAKE_C_COMPILER=gcc

cmake --build build-gcc --parallel
```

В этом режиме применяются общие и GCC-предупреждения, а `-fanalyzer` включён по умолчанию. Остальные дополнительные режимы выключены.

### 5.2. GCC: строгая учебная сборка с санитайзерами

```bash
cmake -S . -B build-gcc-debug \
  -DCMAKE_C_COMPILER=gcc \
  -DCMAKE_BUILD_TYPE=Debug \
  -DENABLE_GCC_ANALYZER=ON \
  -DENABLE_STRICT_ERRORS=ON \
  -DDISABLE_VLA=ON \
  -DENABLE_AGGRESSIVE_GCC_WARNINGS=ON \
  -DENABLE_C_COMPAT_WARNINGS=ON \
  -DENABLE_SANITIZERS=ON

cmake --build build-gcc-debug --parallel
```

### 5.3. Обычная сборка Clang

```bash
cmake -S . -B build-clang \
  -DCMAKE_C_COMPILER=clang

cmake --build build-clang --parallel
```

`ENABLE_GCC_ANALYZER` по умолчанию остаётся включённым в cache, но для Clang анализатор GCC не подключается.

### 5.4. Clang: сборка с дополнительными проверками и санитайзерами

```bash
cmake -S . -B build-clang-debug \
  -DCMAKE_C_COMPILER=clang \
  -DCMAKE_BUILD_TYPE=Debug \
  -DENABLE_STRICT_ERRORS=ON \
  -DDISABLE_VLA=ON \
  -DENABLE_CLANG_UNSAFE_BUFFER=ON \
  -DENABLE_C_COMPAT_WARNINGS=ON \
  -DENABLE_SANITIZERS=ON

cmake --build build-clang-debug --parallel
```

### 5.5. Подробный вывод команд компиляции

`VERBOSE=1` не является флагом GCC/Clang и не должен находиться в `target_compile_options()`.

Для подробного вывода используй:

```bash
cmake --build build-gcc-debug --verbose
```

Для генераторов Visual Studio, Xcode и других multi-config генераторов конфигурация выбирается параметром `--config Debug`:

```bash
cmake --build build-clang-debug --config Debug --verbose
```

## 6. Важные правила работы с CMake cache

1. Один каталог сборки (`-B build-...`) должен использовать один выбранный C-компилятор. Для перехода с GCC на Clang создай новый каталог сборки. Не пытайся заменить `CMAKE_C_COMPILER` в уже сконфигурированном каталоге.
2. Значения `option()` сохраняются в `CMakeCache.txt`. Повторная конфигурация без `-D` сохраняет ранее выбранное значение.
3. Чтобы выключить опцию, явно передай `-DИМЯ=OFF`.
4. Чтобы увидеть значения cache-переменных, выполни `cmake -LA -N build-gcc-debug` либо открой каталог в `cmake-gui`/`ccmake`.
5. После изменения корневого `CMakeLists.txt` достаточно повторно выполнить команду конфигурации; CMake сам перегенерирует build system.

## 7. Ограничения и особенности

- Профиль рассчитан на компиляторы с идентификаторами CMake `GNU` и `Clang`. `AppleClang` имеет отдельный идентификатор и намеренно не включён в текущие generator expressions.
- Некоторые предупреждения эффективнее при `-O1`/`-O2`. В частности, анализ `-Wstrict-aliasing`, часть проверок массивов и потока данных зависят от оптимизации. Поэтому полезно иметь отдельную оптимизированную диагностическую сборку.
- Предупреждения не доказывают наличие ошибки, а отсутствие предупреждений не доказывает корректность программы.
- Флаги `-Wall` и `-Wextra` не включают абсолютно все диагностики. Часть опций в конфигурации задана явно, часть зависит от версии компилятора.
- Если появится новый компилятор или старая версия GCC/Clang, проверь поддержку специфичных предупреждений. Для опциональных флагов конфигурация уже использует `CheckCCompilerFlag`; документация CMake подчёркивает, что успешная проверка говорит о принятии флага компилятором, но не доказывает, что он реально выполняет ожидаемую диагностику.

## 8. Быстрая памятка по опциям

| Задача | Команда |
|---|---|
| Выключить GCC analyzer | `-DENABLE_GCC_ANALYZER=OFF` |
| Включить Clang unsafe buffer diagnostics | `-DENABLE_CLANG_UNSAFE_BUFFER=ON` |
| Включить строгие ошибки | `-DENABLE_STRICT_ERRORS=ON` |
| Запретить VLA | `-DDISABLE_VLA=ON` |
| Включить проверки совместимости C | `-DENABLE_C_COMPAT_WARNINGS=ON` |
| Включить агрессивный GCC stringop check | `-DENABLE_AGGRESSIVE_GCC_WARNINGS=ON` |
| Включить ASan/UBSan (и Clang Integer Sanitizer) | `-DENABLE_SANITIZERS=ON` |

Все параметры можно комбинировать, если они применимы к выбранному компилятору и целевой платформе.
